เริ่มด้วย vision ที่ตรงกัน เห็น flow และ design ก่อนเขียน spec แล้วส่งต่อผ่าน plan และ tickets ไปถึง code, QA และ UAT

คู่มือภาพรวม workflowเรียกครบ loop ผ่าน start

หนึ่ง loop · สามช่วงทำงาน

กล่องสีส้มคือจุดที่ต้องรับคำตอบหรือการยอมรับจากผู้ใช้ ส่วนการส่งขึ้นระบบใช้ approval ของ action นั้น

01 · เข้าใจและเห็นภาพ

02 · เปลี่ยนข้อตกลงเป็นงาน

03 · ตรวจ รับงาน และส่งมอบ

เมื่อ UAT พบ defect → กลับ ticket และ code ที่เกี่ยวข้อง → ตรวจใหม่ → UAT อีกครั้ง

แต่ละช่วงส่งอะไรให้ช่วงถัดไป

01 ask-me — Vision ที่ยืนยันแล้ว

ผู้ใช้ ปัญหา คุณค่า journey หลัก ขอบเขต MVP และสิ่งที่ไม่ทำ ถามทีละ decision และใช้ข้อมูลเดิมก่อน

02 show-me — Flow และ wireframe

แสดงความสัมพันธ์ของหน้าจอและขั้นตอนให้เข้าใจตรงกัน ยังไม่ใช่ production UI

03 design-options — Mockup ที่ผู้ใช้เลือก

ออกแบบด้วยข้อมูลจริงและ state ที่เกี่ยวข้อง ถ้ามี direction ที่เลือกแล้วให้ปรับต่อได้

04 to-spec — ข้อกำหนดและ test cases

เชื่อม vision/design กับ AC-01 และ TC-01 ระบุ precondition, steps และ expected result

05 plan — ลำดับงานและวิธีตรวจ

ทุก AC ต้องมีงานรองรับและวิธีตรวจ ใช้ verification choices ที่ตกลงแล้ว

06 to-tickets — งานที่หยิบทำได้

หนึ่งไฟล์ต่อ vertical slice มี blocker, AC, test case, design reference และ done condition

07 code — งานที่ทำและตรวจแล้ว

หยิบ ticket ที่ไม่มี blocker ทำตาม spec/design ตรวจผลจริง แล้วทำ ticket ถัดไปใน scope

08 QA / review — หลักฐานที่แยกประเภทได้

Tests, screenshot, browser interaction และ security scan ต้องบอกผลที่รันจริง ตรวจ browser ก่อนเสนอ merge

09 Human UAT — สถานะการรับงานจากคน

มี scenario และ expected result ให้ลอง บันทึก accepted, changes requested หรือ pending ตามจริง

10 Delivery readiness — พร้อมส่งต่อหรือระบุจุดติด

ไม่อ้างว่า UAT ผ่านแทนผู้ใช้ PR, merge และ deploy ต้องมีสิทธิ์สำหรับ target/payload ที่จะทำ

ถามเรื่อง QA ครั้งเดียว

ตกลง test cases และ browser QA proof ก่อนเริ่ม code แล้วใช้คำตอบเดียวกันใน spec, plan และ tickets สำหรับ UI แนะนำทั้งสองอย่าง ส่วน check ที่ repo บังคับยังต้องทำ

Screenshot = หลักฐานหน้าตา · Interaction/E2E = หลักฐานพฤติกรรม

เปลี่ยนโจทย์แล้วกลับตรงไหน

เปลี่ยน vision/design → หา AC, test cases และ tickets ที่ได้รับผลกระทบ → ทำหลักฐานเดิมให้เป็น stale → ตรวจใหม่เฉพาะส่วนที่เปลี่ยน ส่วน UAT พบ defect ให้กลับ ticket ที่เกี่ยวข้อง

เริ่มใช้อย่างไร

$spk:start ทำ product นี้ให้ครบ loop ตั้งแต่ ask-me กำหนด vision → show-me → design-options → to-spec → plan → to-tickets → code → QA/review → UAT

Claude Code ใช้ /spk:start · งานเล็กยังใช้ code โดยตรงได้ · ขอหยุดที่ spec/plan/tickets ได้
