# รอยต่อระหว่าง phase

**phase** คือก้อนงานหนึ่งก้อนใน session — ช่วงถามให้ชัด ช่วงลงมือทำ ช่วง QA นิยามมันคลุมเครือโดยตั้งใจ phase จบเมื่อคุณรู้สึกว่า *"เอาละ เรื่องนั้นจบแล้ว"*

**รอยต่อระหว่าง phase** คือช่องว่างระหว่างสอง phase และเป็นที่เดียวที่ควรตัดสินใจเรื่องนี้ ระหว่างกลาง phase ไม่มีอะไรให้ตัดสิน — ทำต่อ หรือแยกงานที่เหลือไปให้ subagent การ compact กลางคัน ทำให้ agent หลุดเส้นเรื่อง

## ห้าทางเลือก

| ทางเลือก | ทำอะไร |
| --- | --- |
| **ทำต่อ** | อยู่ใน session เดิม ไม่สลับ context เลย |
| **`/clear`** | ล้าง context window แล้วเริ่มจากศูนย์ |
| **`/handoff`** | เขียนไฟล์ markdown ที่พกพาได้ แล้วเอาไปเปิด session ที่ไหนก็ได้ |
| **subagent** | ส่งงานไปอยู่ใน context window ของมันเอง แล้วรอรับรายงานกลับ |
| **`/compact`** | บีบอัด context นี้แล้วใช้เป็นจุดตั้งต้นของ session ใหม่ |

## ต้นไม้การตัดสินใจ

ไล่จากบนลงล่างที่รอยต่อ **ข้อแรกที่ตอบว่าใช่ ชนะ**

**1. ทำต่อใน session นี้ได้ไหม** สองอย่างที่ทำให้ตอบว่าใช่: phase ถัดไปต้องใช้ phase นี้เป็น **primary source** หรือยังเหลือ [smart zone](https://www.aihero.dev/ai-coding-dictionary/smart-zone) พอ (~150k token) ให้ phase ถัดไปอยู่ได้ ช่วงถามให้ชัด → ลงมือทำ คือกรณี "ใช่" มาตรฐาน เพราะตอนลงมือต้องการเหตุผลแบบคำต่อคำ ไม่ใช่บทสรุปของมัน การทำต่อไม่มีต้นทุนและไม่เสียอะไร จึงต้องตัดข้อนี้ออกก่อนเสมอ

**2. context นี้ไม่เกี่ยวกับสิ่งที่จะทำต่อไปเลยใช่ไหม** ทุกอย่างใน session นี้ — การสำรวจ การตัดสินใจ ทางตัน — ทิ้งได้หมดหรือเปล่า ถ้าใช่ ให้ **`/clear`** เป็นท่าที่ถูกที่สุดบนกระดาน ใช้เวลาศูนย์และคืน window ทั้งก้อน แถม `/clear` ไม่ใช่ทางเดียวจบ เพราะ session เดิมยังกลับไปต่อได้

ต้นทุนของการตัดสินผิดข้อนี้เป็นแบบไปแล้วไปเลย ถ้า clear context ที่**ยังเกี่ยวข้อง** คุณจะเสีย **เหตุผลเบื้องหลัง** สิ่งที่สร้างไป และไม่มีการอ่าน diff ย้อนหลังแบบไหนเอามันกลับมาได้

**3. ต้องส่งต่อจริงไหม** `/handoff` ใช้แคบมาก จำเป็นเฉพาะตอนที่คุณกำลัง

- ย้ายไป **harness ใหม่** (Claude → Codex)
- ย้ายไป **directory หรือ repo ใหม่**
- ส่งงานให้ **เพื่อนร่วมงาน**
- หรือแตกงานข้างเคียงที่เจอ **กลาง phase** ออกไปโดยไม่ให้งานหลักหลุด

รายการนี้คือทั้งหมด สิ่งที่ `/handoff` ซื้อให้คือ **ความพกพาได้** ถ้าไม่มีอะไรต้องเดินทาง ก็ไม่ต้องใช้มัน

**4. งานนี้ทำแบบไม่ต้องมีคนเฝ้าได้ไหม** ขอบเขตแคบพอจะรันโดยคุณลุกจากคีย์บอร์ดไปเลยหรือเปล่า ถ้าใช่ ส่งไปให้ **subagent** แล้วปล่อย session นี้ไว้เหมือนเดิม การรีวิวอัตโนมัติคือกรณีมาตรฐาน — agent อ่าน diff แล้วรายงาน โดยไม่ต้องใช้คุณระหว่างนั้น

**5. นอกนั้นคือ `/compact`** context ยังเกี่ยวข้อง อยู่ harness เดิม directory เดิม และคุณยังต้องอยู่ในลูป — ต้นไม้จะมาจบตรงนี้ และมาจบตรงนี้บ่อย ให้ส่งคำสั่งกำกับไปด้วย (`/compact เรากำลังจะไป QA ส่วนนี้`) เพื่อให้บทสรุปเก็บสิ่งที่ phase ถัดไปต้องใช้

`/compact` เป็น **ค่าเริ่มต้น ไม่ใช่ท่าแรกที่ควรคว้า** มันอยู่ล่างสุดเพราะสี่คำถามข้างบนถูกกว่าหรือแม่นกว่าทั้งหมด อาการพังของคนที่เริ่มจากตรงนี้เลยคือ session ใหม่ที่มั่นใจเต็มร้อยแต่เข้าใจผิด เพราะบทสรุปกลืนรายละเอียดของ decision ไปแล้ว

## primary source กับ secondary source

ทุกท่ายกเว้น **ทำต่อ** เปลี่ยน **primary source** ให้กลายเป็น **secondary source** — จาก session อย่างที่มันเกิดขึ้นจริง กลายเป็นบทสรุปของมัน การแลกนี้มีรูปร่างเดิมเสมอ

| แหล่ง | ข้อมูล | สิ่งรบกวน | ที่ว่างให้ขยับ |
| --- | --- | --- | --- |
| primary (ทำต่อ) | ครบ | เยอะ | น้อย |
| secondary (`/compact`, `/handoff`) | หายบางส่วน | น้อยลง | เยอะ |

นี่คือเหตุผลที่คำถามข้อ 1 มาก่อน คุณจ่ายค่าความสูญเสียนี้ก็ต่อเมื่อการอยู่ต่อแพงกว่าที่มันประหยัดได้

## ทั้งหมดนี้คือการใช้วิจารณญาณ

คำถามเหล่านี้ไม่ได้เป็นภววิสัย แต่ละข้อมีรสนิยมปนอยู่ และรอยต่อเดียวกันอาจตัดสินคนละแบบในสองวัน คุณค่าอยู่ที่การถามมัน **ตามลำดับ** ที่รอยต่อ ไม่ใช่กลางงาน
